## 1. TL;DR

The broadcast + skew decision is now the **plugin's responsibility** end-to-end. The `BroadcastStub` and `SkewStub` `PreExecute` hooks consult + write the decision into `Context.meta`. The platform's `EngineService.runQueryWithHooks.engineExecutor` thunk folds the post-PreExecute `Context.meta` into a typed `DecisionHints` value attached to `EngineContext.decisionHints`. The spark connector's seed helpers (`seedBroadcastThreshold`, `seedSkewFactor`) consult `decisionHints` first and fall back to the inline presence rule when `None`. Zero SDK surface change (no `Context.meta` strings reach the connector).

The wave went through **three ADR revisions**. v0.1 and v0.2 were both BLOCKED by dual review (4 P1s in v0.1, 2 P1s in v0.2). v0.3 (the implementation spec at PR-173) fixed both v0.2 P1s (the hook try/catch was removed — throwing oracle propagates to the dispatcher's existing catch; the fold was relocated INSIDE the `engineExecutor` thunk). PR-174 shipped the production wiring at all 5 layers (plugins + DecisionHints + EngineContext + EngineService fold + spark connector seed helpers).

**Final state**: full reactor green (15 modules, 220 spark-connector tests + 86 platform tests + 86 broadcast/skew stub tests + 3 DecisionHintsSpec tests). Dual reviewer CORRECT verdict (architect + data-eng, confidence 0.85). 6 review findings fixed at PR-174 + amended head `6701244`. No follow-ups from this ADR.

## 2. What landed

### 2.1 The typed decision channel: `DecisionHints` on `EngineContext`

A new non-SDK core type in `sm8-core/engine/DecisionHints.scala`:

```scala
final case class DecisionHints(
 broadcastArmed: Option[Boolean] = None,
 skewArmed: Option[Boolean] = None,
 broadcastThresholdBytes: Option[Long] = None)
```

Each field is independently Optional:
- `broadcastArmed` is the **FULL** arm decision — `Some(b)` arms or disarms regardless of inline rule.
- `skewArmed` is the **PARTIAL** arm decision — `Some(true)` requires at least one join with `estimatedRows` (a skew factor without an estimated large-row join has no observable effect).
- `broadcastThresholdBytes` is the byte budget in **BYTES** (a row-count value would be misinterpreted as a byte budget and disarm most real joins).

`EngineContext` gains an additive field `decisionHints: Option[DecisionHints] = None`. The existing `defaultContext` works unchanged (the default is `None`, which triggers the inline fallback).

### 2.2 The plugin hooks: value-consult, not presence-ARM

`BroadcastStub.PreExecute.run` (priority 250) reads `context.request.model`, computes the value-consult arm with a private default threshold (`BroadcastThresholdRows = 10M rows`), and writes:

```scala
context.meta + ("sm8.broadcast.arm" -> arm) + ("sm8.broadcast.thresholdBytes" -> BroadcastThresholdBytes)
```

where `BroadcastThresholdBytes = 10 MiB` (distinct from the row-count threshold). `SkewStub.PreExecute.run` mirrors the shape at `SkewThresholdRows = 1B rows`. NO try/catch — a throwing consult propagates to `EngineHookDispatcher`'s existing catch, which constructs `EngineError.HookFailed(engine, name, priority, stage, message)` (5-field, no defaults) from the thrown exception with a sanitized message. The spark connector never sees the hook's exception.

### 2.3 The platform fold: INSIDE the `engineExecutor` thunk

The fold lives inside the `engineExecutor` thunk passed to `dispatcher.run(initialCtx, engineExecutor)` — the only seam where the post-PreExecute `Context.meta` is visible. The executor's first action folds:

```scala
val decisionCtx = EngineContext.defaultContext.copy(
 decisionHints = Some(DecisionHints(
   broadcastArmed          = ctx.meta.get("sm8.broadcast.arm").collect { case b: Boolean => b },
   skewArmed               = ctx.meta.get("sm8.skew.arm").collect { case b: Boolean => b },
   broadcastThresholdBytes = ctx.meta.get("sm8.broadcast.thresholdBytes").collect { case l: Long => l }
 )))
```

The fold is naturally gated: a throwing oracle short-circuits the dispatcher before the thunk runs. `executeEngine` now takes `decisionCtx` as a 4th arg; the spark provider receives it via `EngineContext.decisionHints`.

### 2.4 The spark connector: oracle first, inline fallback

`seedBroadcastThreshold` consults `eCtx.decisionHints.flatMap(_.broadcastArmed)` first; if `Some(b)`, the arm Boolean is the decision; if `None`, the inline presence rule runs. Same pattern for `seedSkewFactor` with `skewArmed`. For broadcast, the oracle's `broadcastThresholdBytes` wins over the session's `autoBroadcastJoinThreshold`; for skew, the `JoinHints.skewFactor = Some(f)` precondition is preserved (a `Some(true)` oracle still needs `Some(f)` to actually write).

## 3. The 3-revision lesson (v0.1 + v0.2 BLOCKED → v0.3)

The v0.3 implementation had to ship three times before clearing:

- **v0.1 (BLOCKED)**: hook sample used presence-ARM (identical to inline fallback), contradicting the "value-consult" claims — the deployment semantics change was fictional; the production wiring never reached `seedBroadcastThreshold` (every production site passes `hookRunner = None`); the `HookFailed` sample was 3-field (won't compile — actual is 5-field); an early `return` inside flatMap reintroduced the v0.5-r1 race.
- **v0.2 (BLOCKED)**: an in-hook try/catch would swallow a Throwable while the on-disk `EngineHookDispatcher` constructs `HookFailed` ONLY by catching a thrown exception (never inspects meta for `*.error` keys) — so the throwing-oracle path would surface as anonymous `ProviderInvocationFailed(NoResult)`; the fold was placed at "after dispatcher returns and before executeEngine", an instant that doesn't exist (`executeEngine` is invoked INSIDE the thunk).
- **v0.3 (rebuilt)**: the hook try/catch is REMOVED — a throwing consult propagates to the dispatcher's existing catch (5-field `HookFailed`); the fold is relocated INSIDE the `engineExecutor` thunk — the executor's first action folds meta into `DecisionHints`.

The dueling dual reviews caught each P1 independently from orthogonal angles (architect vs data-eng vs both). The cost of 6 review cycles is real; the alternative — shipping a non-falsifiable design — would have been worse.

## 5. What worked

1. **Three-revision ADR pattern.** Each BLOCKED version carried the next-attempt plan inline; the reviewer feedback was specific enough to fix in the same revision, not the next wave. The "rebuild from scratch on this ADR" approach (v0.1 → v0.2 → v0.3) closed all blockers in one wave.
2. **Typed transport, no string-meta.** `DecisionHints` is a closed ADT with 3 Optional fields; the platform fold uses `collect { case b: Boolean => b }` to type-check at the boundary. Adapters cannot invent decision names that the plugin cannot classify — the per-RFC §3 boundary is structurally enforced, not just convention.
3. **The dispatcher's existing catch does the work.** Removing the in-hook try/catch meant the throwing-oracle path is handled by `EngineHookDispatcher`'s 5-field construction (the single owner of `HookFailed`). We never construct it manually in the spark connector.
4. **Two-row fold inside the thunk.** The fold is a single `EngineContext.defaultContext.copy(decisionHints = Some(...))` line — not a separate stage. No new platform code beyond the fold line and the 4th `executeEngine` arg.
5. **The 18 falsifiable tests.** 11 in `SparkBroadcastSeedSpec` (broadcast: armed, disarmed, no-oracle, disagreement at small estimate + 100M window; skew: armed, disarmed, no-oracle, disagreement at small estimate + 100M window + 1K small). Plus the 3 DecisionHintsSpec + 6 stub contracts + 5 platform fold tests. Every observer of the wiring has a falsifiable test.
6. **The post-PR review caught what the pre-PR review didn't.** The data-eng reviewer's DE F3 (rows-vs-bytes in the platform spec) was in a 2nd spec file the local review didn't re-check. The amended head `6701244` closed it before merge.

## 6. What didn't work (and what to change)

1. **The local review missed the platform-spec rows-vs-bytes.** Two specs (stub + platform) have the same byte-budget assertion; only one was checked. **Going forward:** any wired-meta assertion change MUST grep all spec files for the changed constant (`grep -rn "10000000L"`), not just the spec under review. The same pattern that bit the v0.5 dead-store (2 file-check, multiple call-site check).
2. **`BroadcastStub.consult` + `SkewStub.consult` are now unused in production.** Both SDK plugins retain the methods (per the SDK `Plugin.setup` API surface) but the production decision is on the hook path, not a direct consult. **Going forward:** either remove the methods (if no plugins depend on them in user code) or document them as "planner pre-flight consult" and add a spec for that shape. For now, retained for backward compat with the SDK surface.
3. **The `lastQuerySessionTL` seam was added in the v0.5 wave (PR-171) but the v0.3 work didn't need it.** The v0.3 tests use `withQuerySessionTL` (the pre-query seam) + the post-query `withLastQuerySession` only when reading conf after `query()` returns. **Going forward:** when adding a new test seam, audit which existing seams cover the same need before adding the new one.
