## Findings

### M-1 (MEDIUM) — Migration path for existing rollup tables carrying `sumsq__F` is not exercised

**Where**: `connectors/spark-connector/src/main/scala/io/sm8/connectors/spark/RollupMaterializer.scala:240-258`
(connector materializer, Welford emit) +
`sm8-core/src/main/scala/io/sm8/core/rel/RollupRewriter.scala:786-810`
(core `stateColumnsFor`, Welford emit) +
the test `"Algebraic state columns emitted for Avg: count__amount, sum__amount, m2__amount (Welford)"`
in `connectors/spark-connector/src/test/scala/io/sm8/connectors/spark/RollupMaterializerSpec.scala:500-513`.

**Observation**: The T8 commit flips the materializer from `sumsq__F` to `m2__F` and the rewriter
guard expressions from cancellation-form to Welford-form. Any rollup table that was materialized
by PR-337 (the pre-T8 state) carries the OLD `sumsq__F` column and lacks `m2__F`.

**On the rewired routing path, the state-columns-availability check is performed**

per-request by `algebraicReaggregation` against `stateColumnNames(spec, model)`. As long as
`spec` carries an Avg/Stddev measure, `stateColumnsFor` synthesizes the EXPECTED column names
(count__F, sum__F, m2__F) regardless of whether the rollup TABLE has them materialized. The
`reconciledRollupSchema` and the connector materializer's `buildRollupDf` are the
physical-table side; the rewriter is logical. **A request lands on an old rollup table that was
written with `sumsq__F` only → `aggregateReaggregable` returns `Right(())` → rewriter emits
`Sum(count__F) AS count__F_total, Sum(m2__F) AS m2__F_total` → Spark fails with
`AnalysisExceptionForUnresolvedColumn[m2__F]` AT EXECUTION, not at planning.**

**Why MEDIUM, not HIGH**: PR-337 was the wiring PR for state columns; in
the same release PR-332 (Spark rollup materialization, 2026-08-27) introduced the
materializer. This is the **first migration that broke back-compat on the wire format**. There
is no public deployment yet to break. But nothing in the test matrix exercises this scenario,
and the failure mode is a runtime AnalysisException, not a typed refusal — exactly the pattern
PR-332 ringfenced in `runtime 02-4-2`.

**Recommendation (NOT a blocker on this PR)**: a follow-up PR should add either (a) a typed
`RollupRewriteRefusal.RollupSchemaStale` that fires when the resolved scan schema lacks the
required state columns (i.e. the rollup TABLE is older than the rewriter version), or (b) a
transparent migration on first read that adds the m2 column and re-buckets group totals. Option
(a) is the conservative closed-ADT extension; option (b) requires a `(count, sum) → m2` map
side-up. ADR-0023 §"Routing contract #1" implicitly required (a) ("matched rollup lacks the
state columns an algebraic measure needs") but only at the spec-declaration level; the
table-level mirror is missing.

Alternatively, gate the migration behind a manifest version bump. Open question for the user —
not a PR-blocker for this PR since there's no deployed rollup to migrate yet.

### M-2 (MEDIUM) — ADR-0023 §"Connectors with their own Expr compilers inherit algebraic routing only after mirroring" is not asserted by any test

**Where**: `docs/adr/0023-aggregate-call-algebraic-routing.md` line 74 (the parallel-arm
checklist mention) + the actual compiler-side change in
`connectors/spark-connector/src/main/scala/io/sm8/connectors/spark/PortableExprCompiler.scala:200-216`.

**Observation**: The adapter-side fix is correct for spark-connector. The contract for OTHER
connectors (Trino, DuckDB when their lowerers land) is "mirror the same builtin arm." This is
ADR-0023's stated cross-engine contract. But the suite that pins this PR doesn't include a
contract test that says: "for any Expr.FunctionCall the adapter does not explicitly allowlist,
the failure mode is a typed `EngineError.UnsupportedCapability`, never a thrown
`Exception` (the legacy throw-bomb)." The previous state in
`PortableExprCompiler.scala:190` (pre-PR-1c)
**was** a throw site; the T8 change replaced it with a typed-Left arm.

**Why MEDIUM, not HIGH**: The PR's spark-connector arm is correct. The cross-engine checklist
will become load-bearing the moment a second engine adapter is built. ADRs are good for
deliberate cross-engine discipline; a typed-error contract test would be better.

**Recommendation**: In a follow-up PR, add a contract test that asserts
`PortableQueryCompiler.compileRelOp` over a rollup-yielding request that exercises
`FunctionCall("sqrt", ...)` returns `Right(DF)` for the spark-connector path. The
`RollupMaterializerAlgebraicSpec.T8 cancellation tripwire` test already does this end-to-end
(`connectors/spark-connector/src/test/scala/io/sm8/connectors/spark/RollupMaterializerSpec.scala:615-690`),
so the contract is implicit; a smaller targeted test focused on the compile boundary
(`compileRelOp` returning Right, not Left) would make the cross-engine checklist
actionable without waiting for the second engine.

### L-1 (LOW, structural) — Dedup logic for state columns re-visits the `(StateColumn, EngineError)` casing question

**Where**:
`connectors/spark-connector/src/main/scala/io/sm8/connectors/spark/RollupMaterializer.scala:262-265`
uses `(additiveCols ++ algebraicCols).groupBy(_.toString).map(_._2.head).toList` as the de-dup
mechanism.

**Observation**: This depends on `Column.toString` for equality. Spark's `Column.toString`
prints the Catalyst expression tree text, which is generally deterministic per-input but
**may not be stable across Spark versions**. The PR-337/pre-T8 shape used the same dedup, so
this is not a T8 regression — but if any future Spark bumps change the printer's whitespace or
parenthesization, dedup silently fails or merges wrongly. The community-accepted stable key
for a Column is its expression Identity (Catalyst `Expression` reference equality), not
`toString`.

**Recommendation**: A follow-up PR should switch to a structurally-stable key. Not a blocker.

### L-2 (LOW, cosmetic) — The two encode sides (stateColumnsFor in core / stateColumns in connector) are split by layer with no test asserting name parity

**Where**: `sm8-core/src/main/scala/io/sm8/core/rel/RollupRewriter.scala:786-810`
(`stateColumnsFor`, emits logical schema) +
`connectors/spark-connector/src/main/scala/io/sm8/connectors/spark/RollupMaterializer.scala:230-258`
(`stateColumns`, emits physical columns) +
the runtime check at `RollupRewriter.scala:534-601` (`stateColumnNames`).

**Observation**: Two pieces of code in two layers emit the same column names by
HUMAN-AUDITED agreement. The runtime availability gate uses `stateColumnNames(spec, model)`
(reading logical schema) for the routing decision; the **physical** rollup table is written
by the connector materializer with names from a SEPARATE function (`stateColumns`). If those
two functions drift, the planner passes a logical check and the runtime dies on an unresolved
column.

The tripwire test that pins this end-to-end (`RollupMaterializerSpec.T8 e2e parity: Avg over
materialized rollup == base path`, line 542-567) catches the drift at the integration level.
This is the right defensive pattern. But there is **no direct unit test that pins
`RollupRewriter.stateColumnsFor` (in core) produces the same column names as
`RollupMaterializer.stateColumns` (in connector) for each AggregateFn shape**. Such a test
would be a 10-line deterministic `shouldBe` against a shared fixture, and would catch drift
at unit-test speed.

**Recommendation**: A follow-up PR could add a unit-level cross-layer invariant test. Not a
blocker for this PR; the E2E parity test covers the contract.

### L-3 (LOW, cosmetic) — The `AlgebraicFragment` inner-call sort is implicit; comment could note it

**Where**: `sm8-core/src/main/scala/io/sm8/core/rel/RollupRewriter.scala:605-611`:
```scala
val innerCalls: List[AggregateCall] = required.toList.sorted.map { sc => ... }
```

**Observation**: `required` is a `Set[String]`; `.toList.sorted` is deterministic (lex order
on the state column name like `count__fare`, `m2__fare`, `sum__fare`). The test pins this
order at `sm8-core/src/test/scala/io/sm8/core/rel/RollupRewriterSpec.scala:454`:
`List("count__fare_total", "sum__fare_total")`. Sorting alphabetically produces that exact
order. Good.

A one-line comment explaining "sorted alphabetically for deterministic plan emission"
would prevent the next reader from "optimizing" the sort away. Cosmetic only.
