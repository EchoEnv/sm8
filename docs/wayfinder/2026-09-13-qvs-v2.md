# Wayfinder map — QueryValidationService v2 (follow-on to #407 / #410)

**Map status**: OPEN (new map)
**Date**: 2026-09-13
**Parent**: wayfinder map #378 (Tier 2+ refinements) — operator-ergonomics + governance axis
**Follows from**: #407 (v1 design), #410 (v1 implementation, merged 2026-09-13 as `31531cb`)
**Stand**: planning only — build is a separate ticket per decision, gated on user go-ahead

## Destination

A spec for **`QueryValidationService` v2** clear enough to build mechanically: four named features (request-dim checking, drift detection, CompiledSQLPreview, MCP exposure) + the platform/connector/core seams each requires + the trade-off each one makes. Resolves every "Q5" follow-up from the v1 ticket; v1 remains the safe-by-construction baseline until v2 is built.

## Why (and why v1 isn't enough)

v1 ships well-formedness + rollup-routing preview. It deliberately stops there because the harder features each require a design decision the v1 grilling explicitly deferred:

- **Q1 — Request-dimension checking against the Model**: v1 passes unknown request dims silently (verified during the v1 spec — core has no such check). Operators can't catch the typo "region" → "reigon" without running the query.
- **Q2 — Schema-drift detection at validate-time**: v1 deliberately trusts the manifest (DeclaredSchemaResolver returns the Model's declared field set, not the warehouse's current state). `ModelValidator.validateAgainstSchema` exists in core but has zero production callers (verified 2026-09-12, seedling r5 #2). A column drop in the warehouse is invisible to validate.
- **Q3 — CompiledSQL preview**: the r1 motivation included "would this route to the rollup or hit the base table" — partially answered by routing preview, but the actual SQL the engine would issue (matters for cost / performance review) is in the connector, not in core.
- **Q4 — MCP exposure of validate**: the v1 handler is HTTP-exposed but the MCP surface (sm8-mcp) doesn't list it. LLM agents that want to validate a query before running it must know the Restate wire protocol, not just the model name.

## Decision tree (D1–D5)

### D1 — Request-dim checking seam

Where does "unknown request dimension" get caught?
- (a) **Core / QueryBuilder**: add a check inside `QueryBuilder.build` (no resolver change). Pure-data check against `model.dimensions.map(_.name)`. ~30 LOC core.
- (b) **Platform / QueryValidationService**: check post-build against the `RelOp` the builder produced. ~20 LOC platform.
- (c) **Both**: defense in depth; core check raises the typed error, platform mirrors for the validate endpoint.

**Trade-off**: (a) catches it earlier in the call chain (build-stage not after-the-fact). (c) is safest but duplicates the check. (b) keeps the change scoped to the new endpoint — a thinner patch, easier to roll back if the core check ever needs to grow.

### D2 — Drift detection wiring

How does `ModelValidator.validateAgainstSchema` get produced callers?
- (a) **Connector / SparkEngineProvider**: call it from `query()` after the source resolver returns, with the resolved `Scan.schema`. Closes the typed-drift gap as a side-effect of normal execute flow. ~40 LOC connector.
- (b) **Platform / QueryValidationService**: validate calls the resolver (declared schema from the model, NOT the warehouse) + a separate `RealSchemaResolver` that calls `spark.table(...).schema`. Side-by-side compare produces the typed drift report. ~120 LOC platform.
- (c) **Both**: a) covers execute-time, b) covers validate-time drift preview.

**Trade-off**: (a) is the right minimal fix for execute-time (the actual production bug); (b) is the validate-time feature, and requires a new resolver variant. (c) is the full picture but the heaviest.

### D3 — CompiledSQL preview

How does validate return the would-be SQL?
- (a) **Move the SQL compiler from the connector to core**: extract `SparkQueryCompiler` to a new `io.sm8.core.rel.SqlCompiler` trait + a typed `CompiledSql` ADT. Core owns the shape; connector owns the dialect. ~200 LOC core + ~150 LOC connector refactor.
- (b) **Add a `compileSql(request)` method to `SourceResolver`**: the connector's existing `SparkSourceResolver` returns the compiled SQL alongside the resolved schema. Validate calls the connector's resolver; the existing `DeclaredSchemaResolver` returns no SQL. ~80 LOC connector + ~30 LOC platform.
- (c) **Defer entirely**: CompiledSQLPreview was a "v2 candidate" in the v1 ticket. The competitive baseline (dbt compile, mf --explain) shows it without SQL preview. Ship without it; let user demand pull the feature.

**Trade-off**: (a) is the right architecture but heavy. (b) keeps the seam close to the data. (c) is honest — dbt/mf's value is the plan TREE, not the SQL string.

### D4 — MCP exposure

How does validate appear to LLM agents via the MCP server?
- (a) **Add `validate` to the MCP tool surface alongside `query`**: reuses the existing transport; the LLM gets `sm8 validate <model>` and `sm8 query <model>` as two distinct verbs. ~40 LOC sm8-mcp.
- (b) **Wrap validate inside the existing `query` tool as an optional `dryRun: bool`**: one tool, two modes; the LLM sets `dryRun: true` to skip execute. ~20 LOC sm8-mcp.
- (c) **Expose validate via a separate MCP tool** (e.g. `sm8_validate`) with its own input schema: same as (a) but explicit, more discoverable in the MCP tool list.

**Trade-off**: (a) is the conventional pattern. (b) hides the new verb inside an existing one — confusing in tool descriptions. (c) is most explicit.

### D5 — Sequencing + build order

Which v2 feature ships first?
- (a) **D2 (drift) + D4 (MCP) together** — drift is the highest-leverage (closes a real production bug) + MCP is the cheapest (no resolver dance). Together they justify v2 as a "production safety + agent usability" release.
- (b) **D1 + D2 + D3 + D4 in a single build** — big-bang; longer review, but the four features are genuinely related (they all touch the same seam).
- (c) **D1 + D2 first, D3 + D4 later** — split v2 into two ships: 2a (correctness), 2b (agent UX). Reviewable in chunks.

**Trade-off**: (a) is right-sized for one review cycle. (c) is the safest (no big-bang), (b) is the riskiest (everything in one PR).
