## 4. Environment trap — aarch64 + Temurin 17.0.14 SIGSEGV

**This is the single most important handover item.** The dev host
(7.5 GiB aarch64, Temurin 17.0.14) crashes the JVM during Iceberg CTAS
writes under **both** bare-java and Maven-harness invocations. Reproduced
4× with three distinct crash sites (JVM-internal, NOT application code):

| hs_err file (in /tmp/d5-mor) | Crash site |
|---|---|
| hs_err_pid1864258.log | netty `PlatformDependent0.directBufferAddress` |
| hs_err_pid1866882.log | netty `PlatformDependent0.directBufferAddress` (same, different run) |
| hs_err_pid1897199.log | JVM `Dictionary::find` (SymbolTable) |
| hs_err_pid2028867.log (from the Maven harness run) | JVM `ConcurrentHashTable::get_node` |

**Reproduction** (as of this writing):

```bash
cd /tmp/d5-mor   # or any clone
GATEB_LIVE_TRACE=true mvn test -pl connectors/spark-connector \
  -Dtest=GateBLiveTraceOnceSpec
# Expect: SIGSEGV during Iceberg CTAS of the 1.05M-row rep_events table
```

**Not fixed by**: `--add-opens` variants (16 opens tried, including
`jdk.internal.misc`, `sun.misc`, `java.nio.buffer`, `sun.nio.cs`,
`sun.security.action`, `sun.util.calendar`); JVM `-Xmx` scaling.

**Hypothesis**: aarch64 + Temurin 17.0.14 JVM bug (SymbolTable /
netty-shaded unsafe access) under concurrent SymbolTable pressure from
Iceberg's manifest reads + Spark's own SymbolTable activity. NOT an
application bug — the same workload passed 416/0 repeatedly when NOT
exercising the Iceberg CTAS path.

**Workaround**: none on this host. Production deployments run
spark-submit on curated JDKs (Temurin 17.0.14 is known-good there per
the ADR-0028 docs) — this is a dev-host limitation only.

**Mitigation used in this arc**: one successful trace run DID produce
`/var/lib/sm8/gate-b/traces/2026-09-11.json` (`isLiveModel: true`) before
a subsequent crash. A 2-week cron cadence CANNOT run on this host.

## 5. Ticket #394 — Restate cron scheduler

Design produced + compiled in the 2026-09-11 session, then **stopped per
karpathy-guidelines** ("smallest correct change") when the test-harness
bootstrap turned out to be more expensive than the feature.

The full design, Restate 2.1.1 ground-truthed API notes, and the
harness-bootstrap estimate are on the ticket:
https://github.com/EchoEnv/sm8/issues/394

Key API notes (verified via `javap` on sdk-{api,common,core}-2.1.1 in
`~/.m2` — the upstream restatedev/examples Java Cron.java uses a NEWER
SDK; these calls do NOT exist in 2.1.1):

- Delayed self-send: `ctx.send(Request.of(Target.virtualObject(...), ...), Duration)`
- `Target` getters: `getService()/getKey()/getHandler()` (not `.service`)
- `Slice.wrap(byte[])` — `Slice.of(...)` does not exist
- `AsyncResult` has NO factory — hand-implement `poll()/ctx()/map/mapFailure`
- The `HandlerRunner.run` test surface accepts the **wire-level**
  `dev.restate.sdk.endpoint.definition.HandlerContext` (sdk-common), NOT
  the SDK-typed `dev.restate.sdk.ObjectContext` — two separate hierarchies
- The `TestHandlerStubs` helper throws on the state methods the cron
  service needs; a cron-shaped stub is purpose-built

Harness-bootstrap estimate: ~2× a typical docs/test PR.
